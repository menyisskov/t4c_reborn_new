# Native pursuit probe (T4C-0212 preparation)

`NativePursuitProbe` is a bounded, two-adapter check for a future **integrated** moving-creature server. It is currently source preparation only. Do not run it against the existing stationary-creature server or record a pass until the cohesive pursuit candidate has been built and given its own resource window.

The probe uses two real `OnlineConnection` instances. It provisions separate standard warrior kits and online accounts through `OnlineStore`, creates two external private profile files, and acknowledges each native region. Observer B joins first and waits for the passive, nonstationary Olin Haad guard authored at world 0 `(2935,1041)` to enter a measured east-of-attacker melee window whose west retreat endpoint is reachable by the guard. The probe then provisions a **fresh operator fixture** attacker A at legal world position `(2934.5,1041.5)`, on the guard's west flank; it does not move an existing character or claim normal player creation UI coverage. It derives the guard's stable region-order local ID from the bundled spawn list and checks the **live public position**, melee distance, line of sight and radius-one A* path with its goal-cell exception before one accepted hit. The hit must commit that guard life with A as its target. From A's actual fractional post-hit position, the probe verifies a straight west ray for at least three tiles plus a half-tile margin against player collision, sanctuary terrain and the guard's reachable endpoint. A sends only west input until its authoritative position advances three tiles, then stops without waypoints, diagonal input or recentering; death, respawn and location-epoch changes fail the run. B must see the same guard close by more than eight physical pixels while A stays within two pixels across at least three advancing snapshots and 500 ms. B's committed HP, global position and progress remain unchanged. After at least five seconds the probe matches a durable guarded creature checkpoint (life, HP, current absolute position, mode, target epoch and revision) against B's public region-local view. After normal lease release A's native private view must match its committed HP, global position, progress and balances. The probe then gracefully stops and restarts its **owned** server from the same copied candidate, checks the same committed living guard pose/HP/life, and rejoins both accounts after real lease expiry. Post-restart private comparisons poll for at most eight seconds for ordinary native snapshot delivery while still requiring exact committed fields. It never clears a lease or replays an uncertain attack.

## Isolated candidate and command

The operator must first reserve port `18771`, a fresh `t4c_pursuit_0212_*` database on the existing PostgreSQL service at `127.0.0.1:55432`, and create-only output and runtime directories under the user's private TEMP. Keep QA `18765`, the other probe ports/databases, the shared PostgreSQL service, root Maven/target outputs, and the desktop untouched. Do not use personal saves or profiles. Build client and server from one immutable **committed base plus explicit WIP candidate copies** while T4C-0212 remains uncommitted; record the base SHA and SHA-256 of every copied candidate source in `RUNTIME/candidate-manifest.tsv`. The probe requires its first line `baseCommit<TAB><40 lowercase hex SHA>` and at least one following `candidateSource<TAB><64 hex SHA256><TAB><repo-relative path>` line. These source hashes are operator-supplied build provenance, not independent proof of the copied JAR's inputs; preserve the isolated build archive/log and verify them before acceptance. Copy the resulting matching server JAR, desktop `T4C.jar`, dependency JARs and normal world/dungeon collision layout into the runtime. The probe measures the manifest/JAR hashes, protocol and schema; never call the WIP candidate an exact committed base build. It starts its own `ServerMain --online` child at loopback `18771`, waits for persistent health and measured schema 11, then uses a private generated control token and exact process handle for each graceful stop. Set `T4C_DB_URL`, `T4C_DB_USER` and `T4C_DB_PASSWORD` in its environment privately; never put credentials in arguments or logs. No server should already listen on the reserved port.

From a shell with those private variables already set, compile this source against the **same copied candidate** (no Maven or root target write):

```powershell
$runtime = 'C:\Users\<user>\AppData\Local\Temp\<unique-pursuit-runtime>'
$out = 'C:\Users\<user>\AppData\Local\Temp\<new-pursuit-output>'
$baseCommit = '<40-character-committed-base-SHA>'
$cp = "$runtime\client\T4C.jar;$runtime\t4c-server.jar;$runtime\lib\*;$runtime\client-lib\*"
javac --release 21 -proc:none -cp $cp -d "$runtime\probe" multiplayer/tools/NativePursuitProbe.java
java '-Djava.awt.headless=true' -cp "$runtime\probe;$cp" com.perso.T4C.server.NativePursuitProbe $runtime http://127.0.0.1:18771 $out $baseCommit
```

Create `$runtime\probe` only within the copied runtime. `$out` must **not** exist before execution; the tool creates it and preserves reports and profiles on both pass and failure. The database URL must name `t4c_pursuit_0212_*` exactly; the tool refuses other database names, nonloopback endpoints and inherited TLS/public-origin settings. Its classpath must stay inside the copied runtime. `BASE_COMMIT` and each source-hash manifest entry are operator claims; the probe measures the manifest hash, actual JAR hashes and schema. Independently verify the source-to-JAR match and record exact build/run commands in `ACCEPTANCE.md` after an actual run.

Output files include `report.txt` (sanitized stage, coordinates, health/progress hashes, versions and JAR hashes), `player-a.json` / `player-b.json` (private credentials), `control-*.token` and child logs. Never print or attach profile, control or raw log contents. Each profile is directly usable through the packaged native launcher's `-Profile` argument or `T4C_ONLINE_PROFILE`, **after** the probe closes its adapters and the lease has released. Preserve a failed report and its dedicated database for RCA. Stop only the explicitly owned child server by its private control/process handle; do not stop PostgreSQL or a shared QA server.

## Scope of evidence

An eventual pass proves committed passive-guard provocation, server-authored guard movement closing on settled stationary A in B's native snapshot, B isolation, durable creature checkpoint, A's normal reconnect and same-candidate graceful restart recovery of living guard pose/HP/life. It does not prove rendered movement, natural aggressive acquisition, target contention, full wall navigation, sanctuary or return behavior, death/respawn, in-flight stale-CAS races, displaced drop/quest credit, forced-restart recovery, abilities, or the full two-rendered-client M4/M6 and 20-player Beta gates. The current world-0 crop has no `6`/`7` sanctuary tile; Olin's 60-tile retaliation leash cannot be exceeded there without artificial content, so do not invent a reset test. A deterministic service test should gate an in-flight checkpoint against death/epoch clear. This route asserts traversable player cells and observed creature positions, not a complete wall-path/return contract.
